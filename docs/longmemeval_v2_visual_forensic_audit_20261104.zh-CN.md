# LongMemEval-V2 视觉题逐项复核

本次核查针对提交 `4d9a90b5036defeac4d73d7cd59a5eb4f5971acb` 中的视觉召回第一版和已固定的 8 道新题。结论是：存在可复核的证据流缺陷，低分不能全部归因于底座模型。原始 2/8 分数、模型输出及参考答案均保持原样。

本次没有调用模型或在线 tokenizer。对 8 条视觉 Harness 记录使用保存的响应重放全部输入，核对实际最终提示、图片 SHA、卡片来源及评分记录；另查看 6 道错题的原图和若干历史原图。下面的反事实只改变离线检索条件，没有生成新答案，也不是新的准确率实验。

## 可排除的直接原因

- 六道错题最终生成均为 `finish_reason=stop`，实际输出分别为 242、122、389、118、346、72 tokens，预留输出均为 4096。没有本轮输出截断。
- 六题最终请求在保留 4096 输出后，仍分别剩余 2451、2666、1694、4101、1432、2951 个准入 tokens；请求均在既定预算内。
- 六题题图感知 JSON 均解析成功。逐图查看时，搜索语法、空条件、当前设备、Creative Cloud 页面、活动分类过滤器及相同默认地址等关键可见事实与感知结果基本对应。这不等于建立了全面 OCR/视觉识别真值，但未发现足以解释全部六题的共同读图故障。

当前主要问题发生在读图后的证据路由、事件理解、追检结果更新以及最终答题约束。

## 已确认的实现问题

### 1. 后到证据无法替换先到证据

`18b91103` 和 `f2b221fd` 均进行了二轮 review。第二轮分别引入 6 张新卡，最终均保留 0 张新卡。第二轮 review 明确选中的卡片，分别有 6 张和 1 张没有进入最终答题请求。

原因是先将旧 `pinned` 放在新 `selected` 前面，再按最多 4 张锁定卡截断；最终将锁定卡与按插入顺序排列的 `bank` 拼接，取前 6 张。旧卡一旦先占满，追检即使找到新候选，也没有替换渠道。

代码位置：[锁定卡选择](../long_context_agent/visual_anchor_memory.py#L259)、[最终 bank 前缀截断](../long_context_agent/visual_anchor_memory.py#L280)。

原有 `pinned_omitted=[]` 只证明已锁定的旧卡没丢，漏报了“新一轮已选卡没有进入锁定集合”的情况。此前的重放通过验证了程序按记录执行，不能证明相关证据完整保留。这是审计覆盖缺口。

但不能因此断言只修保留机制就会答对：Photoshop 题的二轮候选仍主要是 Catalog Items 页面，本身没有取得关键硬件配置页。

### 2. review 的缺口和冲突没有可靠影响最终回答

六道错题的最后一次 review 都给出了非空 `missing`；五题同时给出 `complete=true`。其中四题最后仍有非空 `conflicts`。程序在 `complete=true` 时直接退出追检，并未处理这些字段之间的矛盾。

`f2b221fd` 更明确：最后仍是 `complete=false`，有 3 个后续搜索和未解冲突。达到轮数上限后，最终提示仍只包含初始 perception、原始卡片和配对信息，没有结构化传递最后的 `missing/complete/conflicts`，模型随后断言错误分类。

代码位置：[无条件采用 complete 停止](../long_context_agent/visual_anchor_memory.py#L278)、[最终提示内容](../long_context_agent/visual_anchor_memory.py#L208)。

不能简单改成“missing 非空就拒答”：现有 schema 把必需证据缺口与可选追检建议都放进了同一字段。应拆分必要事实缺口、可选搜索和未解决冲突，并把它们明确带入最终答题。

### 3. 事件解析不覆盖真实历史动作

在 5095 个历史状态中，有 4895 条非空动作记录。现有白名单遗漏了：

| 动作 | 数据中的记录数 | 影响 |
|---|---:|---|
| `press` | 211 | Enter、Tab、键盘操作无法作为该类转移进入索引 |
| `clear` | 11 | 清空字段的操作被遗漏 |
| `tab_focus` | 236 | 焦点移动、失焦与表单提交的关联被遗漏 |
| `focus` / `dblclick` / `new_tab` | 6 | 其他合法 UI 事件未覆盖 |

这与有意排除 `send_msg_to_user` 等代理结论不同。另有 260 条 `noop`，其中等待后的稳定状态可能有价值，也不能把“动作后下一帧”默认视为最终效果。

数据还有 27 条无法按简单 Python 调用解析的动作，其中 26 条带有 think/action 标签。`81180ae9` 实际收到的一张历史卡，其 `action_leading_into_this_state` 包含代理叙述与标签；解析器将其排除，但最终渲染仍把原字符串作为“动作”送入模型。需要先规范化事件，将无法确认的叙述明确标为非观察证据。

代码位置：[动作白名单](../long_context_agent/visual_anchor_memory.py#L41)、[原始 action 渲染](../long_context_agent/visual_anchor_memory.py#L205)。

### 4. 时序任务被路由为静态页面检索

六道错题的 `transition_needed` 全为 false，其中至少五道明确询问搜索或表单操作的效果、提交过程、软件配置流程或地址更新影响。于是程序优先检索相似静态页面，而非验证操作前后的结果。

地址题的离线对照非常具体：保持问题、索引和检索词不变，只把该标记改为 true，候选即包含历史 `17c38707/3` 的 Edit Address 状态；其原始观察明确同时标记“默认账单地址”和“默认收货地址”。原路由只取了地址簿/My Account 等页面，没有这条关键事实。

但是强制所有题使用转移并不是完整修复。Photoshop 题在同样的离线改动后仍没取到 Photoshop 控件；此前第二版开发集也从 7/12 回归到 6/12。需要按问题所缺的关系选择静态、转移或多步工作流证据。

### 5. 当前实体与历史类比被混为一谈

`50d92f55` 的题图是设备 A；最终历史卡全部来自另一设备 B。最终答案据此声称用户编辑错了设备。历史中的另一条记录不构成当前用户实际操作过该记录的证据。

review 已指出当前记录与历史记录不同、也没有看到成功保存的过程，但这些限定没有进入最终提示。代码构造检索词时使用了 `retrieval_queries`、问题和可见标签，没有使用 `visible_state_facts` 中的具体实体值，也没有建立“同一实体／仅为同类操作示例”的作用域。

代码位置：[检索词构造](../long_context_agent/visual_anchor_memory.py#L188)。仅加入更多名字并不能解决全部问题，还需限制历史事实可以被用来证明什么。

### 6. 保留文本卡不等于保留对应原图

最终有 6 张文本卡，历史图片只按卡片顺序取前 3 张。按实际 PNG SHA 核对，4 个样本的已锁定卡有原图未进入最终请求，其中 3 个样本是错题，另 1 个是答对的论坛题。不是同图以其他卡 ID 出现造成的假阳性。

这说明现有“卡片未丢”指标不足以判断视觉证据是否可见，但不证明这些错题都是缺图导致。若事实已经由完整可见的观察文本支持，未重复附图未必有害；若需要像素信息或操作后状态图，就应按事实需求分配图片，而非按插入次序。

代码位置：[图片按顺序限额](../long_context_agent/visual_anchor_memory.py#L213)。

## 评分与说明需要同时校准

1. 旧报告“本轮均为 LLM 裁判”的表述不准确。8 道新题中，7 道为 `llm_gotchas_checker`，1 道为 `norm_phrase_set_match`。JSON 原本已记录了正确评分函数；本次只纠正文档及生成器，2/8 分数没有变化。
2. `f2b221fd` 的参考规则允许除 Grocery 之外的其他根分类猜测，也接受明确的“不知道”。它衡量避免特定错误前提的能力，不是唯一根分类精确匹配。因此不能把整组分数直接当作普通 OCR 或分类识别准确率。
3. `is_unknown('UNKNOWN')` 为 true，但 `is_unknown('I do not know')` 为 false。当前 wrapper 对 UNKNOWN 跳过评判直接记错，而最终策略统一要求证据不足时输出 UNKNOWN；这与允许自然语言拒答的题目存在契约不一致。该题本轮实际答了错误分类，没有输出 UNKNOWN，因此这不是重改本轮分数的依据。

评分代码位置：[UNKNOWN 预处理](../scripts/benchmark_longmemeval_v2_visual_anchor.py#L378)。后续应保留不可回答状态与文本表面的区别，按各基准的正式规则适配，分别报告正确实答、允许的拒答和错误实答。

## 修复优先级与验收条件

1. **先修证据更新与缺口传递。** 新一轮已选证据必须有机会替换旧卡；缺口、冲突及当前事实账本须进入最终请求。验收要检查 `selected_late_in_final`、未解决必要事实以及事实对应的图片是否实际可见，不能只检查旧 pinned ID。
2. **补事件规范化与结果链。** 兼容数据实际存在的 press/clear/tab_focus 等动作，区分 UI 调用、等待、代理叙述；取“编辑→触发表单状态变化→保存→回到列表验证”的多步结果，不能只用相邻静态帧或按钮存在证明成功。
3. **建立实体和类比作用域。** 明确当前记录与历史记录的身份关系；类比可帮助解释控件机制，不能反推用户实际编辑了哪条历史记录。
4. **再做问题驱动的检索与预算分配。** 为候选路径及反证保留位置，降低重复错误页面的优先级；按事实需求附原图。地址题的离线检索对照证明路由可以改变可用证据，Photoshop 对照也证明只开时序开关不够。
5. **随后才进行新一轮效果评测。** 当前 8 题已用于诊断，修复后的这组复测只能算回归。泛化结论应使用另一批未参与调优的题，保留既有正确题回归以及 query-only/旧版/新路径对照。

没有证据支持“只扩大窗口、增加多候选投票或增加输出预算就能修好这些问题”。本次已明确验证的是数据与控制流程缺陷，以及若干本来存在但未被送达的关键历史证据；修复后的准确率仍需重新测量。

未修改原模型控制器、冻结结果、参考答案或计分函数，也未产生新的模型调用。本次新增的是诊断材料，以及既有报告中评分组成的一处文字纠正。此核查不等于对真实 ServiceNow/Magento 站点执行了操作或验证了所有参考答案。
